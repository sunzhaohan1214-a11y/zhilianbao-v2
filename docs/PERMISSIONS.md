> 版本：v1.3
> 状态：开发基线（已确认）  
> 产品版本：智链宝 V2.0  
> 依据：PRD v1.3 §3、§4、§6–§20、§28，以及已确认 TECH v1.0

## 1. 权限模型总原则

智链宝不是简单的“管理员 / 非管理员”二级权限。

任何服务端业务操作必须统一经过以下五层判断：

1. **账号与会话有效**
2. **角色动作权限有效**
3. **数据范围 / 业务关系有效**
4. **当前业务状态允许该动作**
5. **敏感权限 / 高风险授权有效**

任何一层不满足，服务端必须拒绝。

前端隐藏按钮仅用于改善体验，**不能作为安全措施**。即使用户自行构造 API 请求，服务端仍须完整执行权限判断。

统一概念函数：

```ts
authorize({
  actor,
  action,
  resource,
  context
}) -> ALLOW | DENY(reason)
```

所有业务模块不得自行绕过统一 Permission Service。

## 2. 权限判定优先级

### 2.1 Deny 优先

以下情况直接拒绝，不再根据其他角色放行：

- 账号处于“待启用”且尚不能登录；
- 账号处于“已停用”；
- 首次登录尚未完成强制改密及保密确认；
- 密码重置后强制改密尚未完成；
- Session 已过期、被踢出或已失效；
- 支撑权限的数据关系已失效；
- 当前业务状态明确禁止该动作；
- 资源已合并、撤回、取消、停用且当前动作不允许在该状态执行；
- 用户没有相应敏感权限。

### 2.2 多角色合并

同一人员可以同时拥有多个有效角色，使用同一账号。

系统自动合并允许的动作和数据范围，不要求用户切换身份。

例如：

```text
在任团员 + 管理员
=
既能认领需求
又能审核需求
```

但以下敏感能力**不得因为普通角色叠加而自动获得**：

- 报销管理；
- 完整审计；
- 备份与恢复；
- 高权限账号管理；
- 系统级敏感配置；
- 个人 AI 对话正文（任何管理员均不能查看他人正文）。

### 2.3 不设置“禁止自审”硬限制

只要当前账号拥有合法管理员权限，即可处理本人此前录入的普通业务。

但所有管理员直录、审核、纠错、状态修正及后续处理必须完整审计。

报销线上只是材料核对与流转记账，不代表财务审批，也不设置系统自审硬限制。

## 3. 角色与特殊权限

### 3.1 基础角色代码

| 角色代码 | 中文名称 | 第一阶段 |
|---|---|---|
| `MEMBER_CURRENT` | 在任团员 | 启用 |
| `MEMBER_ALUMNI_PLATFORM` | 平台内往届团员 | 启用 |
| `GROUP_LEADER` | 团长 | 启用 |
| `MINISTER` | 部长 | 启用 |
| `TOWNSHIP_STAFF` | 镇区工作人员 | 启用 |
| `DEPARTMENT_STAFF` | 部门工作人员 | 启用 |
| `ADMIN` | 管理员 | 启用 |
| `SUPER_ADMIN` | 超级管理员 | 启用 |
| `LEADER_STAGE2` | 第二阶段领导 | 仅预留底层模型，第一阶段不开放完整工作台 |

“历史往届团员”没有平台账号，不是可登录角色，只作为人员档案与后备匹配对象。

### 3.2 团长角色

团长必须：

- 来自当前活动批次的在任团员；
- 使用本人原账号；
- 在 `MEMBER_CURRENT` 基础上叠加 `GROUP_LEADER`；
- 团长任命和撤销由超级管理员执行；
- 任期 / 批次失效后，团长附加权限立即失效。

仅持“在任团员 + 团长”角色时：

- 不审核需求；
- 不修改镇区需求；
- 不取消需求；
- 不转交需求负责人；
- 不查看他人报销；
- 不查看他人办事求助。

若同账号同时拥有管理员等其他合法角色，则按权限合并处理。

### 3.3 部长角色与团队协调能力包

部长必须：

- 使用本人既有 `Person + Account`，不得创建共享账号；
- 由超级管理员显式授予、调整或撤销独立的 `MINISTER`；
- 不得由组织职位名称“部长”自动推断角色；
- 授权保存 `effective_at`、`expired_at`、`granted_by_person_id` 和 `reason`；
- 撤销或失效后立即刷新权限版本，并保留完整授权历史和审计。

第一阶段定义统一能力包：

```text
TEAM_COORDINATOR_CAPABILITIES
```

由以下两个独立角色共同映射：

```text
GROUP_LEADER
MINISTER
```

能力包包含：

- 查看全县已发布业务与全团工作数据；
- 查看全团概览、当前在宝和今日行程；
- 查看、下载全县月度工作台账；
- 创建全团共享行程；
- 对久未更新需求提醒主责。

权限实现不得复制两套相同判断；授权历史、页面标签、日志和审计仍必须保存实际角色代码，不得把 `MINISTER` 记录为 `GROUP_LEADER`。以后两者能力出现差异时，通过各自角色到能力的映射单独调整。

`MINISTER` 不自动赋予 `MEMBER_CURRENT`。仅持 `MINISTER` 时，不得认领或协同需求、申请报销、新建办事求助，也不得获得管理员审核、修改镇区需求、取消需求、负责人转交、报销管理、他人报销或求助可见性、完整审计、备份恢复、他人荷宝 AI 私人正文等能力。部长同时持有 `MEMBER_CURRENT`、`ADMIN` 或其他有效角色时，仅通过多角色合并获得对应能力。

### 3.4 特殊权限代码

以下不是普通组织角色：

| 权限代码 | 含义 | 授权主体 |
|---|---|---|
| `reimbursement.apply` | 当前是否允许新建报销 | 在任团员按产品规则默认具备；平台注册往届可由管理员或超级管理员按人开启 |
| `reimbursement.manage` | 报销线上核对与材料流转 | 超级管理员 |
| `audit.full_view` | 查看完整系统审计 | 仅超级管理员能力 |
| `backup.manage` | 查看和管理备份 | 仅超级管理员能力 |
| `backup.restore` | 执行数据恢复 | 仅超级管理员能力 |
| `system.high_privilege_manage` | 高权限账号和核心敏感配置 | 仅超级管理员能力 |
| `ai.service_manage` | AI/OCR供应商、模型和运行参数 | 仅超级管理员或产品明确授权的高权限能力 |

第一阶段不提供“任意自定义角色编辑器”来改变核心角色语义。

## 4. 组织任职与角色关系

### 4.1 组织任职不自动产生高权限

以下高权限不得由“职位名称”自动推断：

- 管理员；
- 超级管理员；
- 报销管理；
- 团长；
- 部长；
- 第二阶段领导。

这些必须独立授权并记录：

- 授权人；
- 原因；
- 生效时间；
- 失效时间；
- 影响范围；
- 操作审计。

### 4.2 普通组织权限可以来源于有效任职

镇区、部门基础角色及数据范围可以由有效任职关系支撑：

```text
人员
  ↓
有效任职
  ↓
镇区 / 部门
  ↓
基础角色
  ↓
数据范围
```

任一依赖关系失效时，相关权限必须立即失效：

- 任职失效；
- 角色授权失效；
- 部门负责镇区关系失效；
- 当前批次资格失效。

历史业务署名继续保留，不因权限失效而修改历史记录。

## 5. 数据范围模型

统一数据范围代码：

| Scope | 含义 |
|---|---|
| `SELF` | 仅本人业务 |
| `GLOBAL_PUBLISHED` | 全县已发布的内部正式资源 |
| `TOWNSHIP` | 当前有效任职镇区业务 |
| `DEPARTMENT_TOWNSHIPS` | 当前部门负责的镇区业务 |
| `GLOBAL_OPERATIONAL` | 全县日常运营数据，不包含专属敏感数据 |
| `REIMBURSEMENT_AUTHORIZED` | 报销管理授权范围 |
| `SYSTEM` | 系统级配置、审计、备份等 |
| `LEADER_SCOPE` | 第二阶段领导数据范围，第一阶段只预留 |

### 5.1 镇区范围

镇区工作人员可以：

- 查看全县正式资源；
- 处理本镇组织业务；
- 不得修改其他镇区业务。

### 5.2 部门范围

部门工作人员：

- 可以查看全县正式资源；
- 对其部门当前负责的镇区拥有查看、协调、督办、统计和台账权限；
- 不直接修改镇区录入的需求；
- 部门负责镇区采用多对多关系；
- 负责关系结束后立即收回旧范围；
- 当前负责部门仍可查看其负责镇区的正式历史数据以便接续。

### 5.3 管理员范围

管理员：

- 拥有全县日常运营数据；
- 不因管理员身份自动获得报销、个人 AI 对话、完整审计和备份等专属敏感数据。

### 5.4 超级管理员范围

超级管理员拥有：

- 全部依法可见业务数据；
- 系统级配置和高权限管理。

但仍有不可突破的隐私边界：

> **个人荷宝 AI 完整对话正文始终仅对话本人可见。**

## 6. 全局可见性基线

### 6.1 所有内部登录用户可查看

以下正式资源对所有有效内部账号开放：

- 正式企业；
- 企业正式联系人及完整联系电话；
- 团员档案及联系方式；
- 正式人才；
- 人才原推荐人 / 内部联系人联系方式；
- 政策；
- 已发布正式需求；
- 正式需求附件。

### 6.2 发布前需求和线索

企业公开填报、团员走访线索，在正式发布前仅以下人员可见：

- 负责镇区全部在岗工作人员；
- 管理员；
- 超级管理员。

### 6.3 AI 推荐名单

AI需求推荐仅以下主体可见：

- 管理员 / 超级管理员；
- 负责镇区；
- 被推荐本人。

历史往届无账号对象的推荐，仅：

- 管理员；
- 负责镇区。

### 6.4 报销

报销记录仅：

- 申请人本人；
- 拥有 `reimbursement.manage` 的人员；
- 超级管理员。

普通管理员无特殊授权不得查看。

平台内往届即使当前没有新建报销权限，也仍可查看本人历史报销。

### 6.5 办事求助

仅：

- 提交人；
- 当前处理人员；
- 当前被转交单位的有效工作人员；
- 管理员；
- 超级管理员。

### 6.6 荷宝 AI

完整会话：

- 仅对话本人。

管理端只能查看脱敏汇总，例如：

- 调用次数；
- 成功 / 失败；
- 耗时；
- 模型；
- 功能；
- 反馈；
- 脱敏错误信息。

不得提供“管理员查看完整私人对话正文”功能。

### 6.7 草稿

个人手工新建且未提交草稿：

- 创建人；
- 管理员。

企业公开填报、走访线索、待补充记录、审核退回件及由其形成的组织草稿：

- 负责镇区全部在岗工作人员；
- 管理员。

允许同镇工作人员接续处理，不绑定最初经办人个人。

# 7. 需求模块权限

```text
demand.claim

demand.collaboration.manage
demand.progress.add
demand.close.submit
demand.close.review
demand.cancel
demand.correct_formal
demand.recommendation.manage
demand.owner.transfer
demand.team_coordinator.remind
demand.outcome.fill
demand.outcome.review
```

action code 是技术映射，不改变 PRD 业务语义。

## 7.2 各角色关键能力

### 在任团员

允许：

- 查看全部已发布正式需求；
- 从完成的企业走访中提交需求线索；
- 在符合资格时主动认领“待对接”需求；
- 申请 / 接受协同；
- 成为主责后更新进展；
- 提交办结；
- 作为协同人员补充进展；
- 主责邀请协同、确认协同申请、移除协同；
- 企业纠错。

禁止：

- 正式发布需求；
- 正式新增企业；
- 审核需求；
- 转交主责负责人。

### 平台内往届团员

允许：

- 查看已发布正式需求；
- 在进入往届补充推荐且本人被推荐时选择“愿意协助”或“暂不参与”；
- 作为往届协助人补充进展；
- 企业纠错。

禁止：

- 成为正式主责；
- 主动抢占在任团员认领流程；
- 正式审核发布。

### 团队协调角色

`GROUP_LEADER` 与 `MINISTER` 通过 `TEAM_COORDINATOR_CAPABILITIES` 均可查看全团需求概览，并对符合“久未更新”规则的需求提醒当前主责。

其中 `MINISTER` 不因团队协调身份自动获得认领、协同、进展提交或办结提交能力；这些动作必须来自其同时持有的 `MEMBER_CURRENT` 或其他合法基础角色。

### 镇区工作人员

允许处理本镇：

- 企业公开填报线索；
- 团员走访线索；
- 待关联企业线索；
- 正式需求录入；
- 退回修改；
- 线索补充；
- 转正式草稿；
- 成效填报；
- 符合规则时取消需求；
- 往届协助路径中的镇区经办；
- 往届协助路径代提交办结。

不得：

- 审核正式需求；
- 修改其他镇区需求；
- 人工改写 AI 推荐名单。

### 部门工作人员

对负责镇区：

- 查看；
- 协调；
- 督办；
- 统计。

不得：

- 直接修改镇区需求；
- 正式审核；
- 直接替代镇区成为需求流程责任主体。

### 管理员

允许：

- 审核正式需求；
- 通过 / 退回；
- 管理推荐名单；
- 运营调度；
- 管理员代录并直接确认发布；
- 待办结审核；
- 成效审核；
- 合规业务纠错；
- 发布后正式内容纠错（必须原因、版本、审计、通知）。

管理员在正式发布前：

- 不直接修改企业、联系人、标题、企业原始需求文本等核心字段；
- 应退回负责镇区修改。

管理员正式发布后：

- 经线下核实可以进行正式纠错；
- 必须保留原版本和纠错原因。

禁止：

- 强制转交正式需求负责人。

### 超级管理员

继承管理员能力，并独占：

```text
demand.owner.transfer
```

负责人转交必须：

- 线下确认；
- 输入原因；
- 影响预览；
- 二次确认；
- 直接生效；
- 不要求新负责人线上接受；
- 完整审计。

## 7.3 认领并发规则

一条正式需求只能有一个当前正式主责。

多人同时认领时，服务端必须使用事务 / 唯一约束 / 锁确保：

> 第一位合法提交成功的人获得主责，其余请求明确失败。

不能只依靠前端按钮变灰。

## 7.4 协同关系权限

- 主责可邀请协同人员；
- 其他符合条件团员可申请协同；
- 主责确认申请；
- 协同人员可主动退出并填写原因；
- 主责可移除协同并填写原因；
- 退出 / 移除不得删除历史进展和贡献；
- 相关人员收到消息。

## 7.5 往届协助

往届协助路径启用条件：

- 在任无人适配，或
- 完整认领周期后仍无人认领。

平台内往届只能在适用路径中：

- 愿意协助；
- 暂不参与。

往届不成为正式主责。

管理员确认协助后：

- 负责镇区成为流程责任单位；
- 指定镇区经办人；
- 镇区经办人负责持续更新及代提交办结。

## 7.6 团队协调角色提醒

团长与部长允许：


# 24. API 层强制规则

## 24.1 禁止仅前端鉴权

错误：

```ts
if (user.isAdmin) showApproveButton()
```

然后 API 不检查。

正确：

```ts
await permissionService.require(
  actor,
  "demand.review",
  demand
)
```

## 24.2 禁止业务模块硬编码角色

避免：

```ts
if (role === "ADMIN") ...
```

优先：

```ts
requirePermission("demand.review")
```

角色 → 能力映射集中管理。

## 24.3 数据查询必须带 Scope

任何列表查询不允许：

```ts
prisma.demand.findMany()
```

后续再前端过滤。

必须在服务端查询阶段应用数据范围。

例如：

```text
镇区用户
→ WHERE responsible_area_id IN actor.scope

部门用户
→ WHERE responsible_area_id IN current_department_areas
```

## 24.4 业务状态必须在事务内再次判断

不能：

1. 页面加载时看到“可认领”；
2. 10秒后用户点击；
3. API不查最新状态直接更新。

API事务中必须重新读取并验证当前状态。

# 27. 必须自动化测试的权限用例

以下是 V2 UAT / 自动测试强制项。

## 27.1 账号

- 待启用账号不能登录；
- 未激活账号完成首次登录后只能先改密；
- 强制改密未完成时所有业务API拒绝；
- 第三台设备登录后最早设备失效；
- 密码重置后所有旧Session失效；
- 任职失效后旧镇区 / 部门范围立即失效；
- 高权限撤销后权限立即失效。

## 27.2 需求

- 普通团员不能审核需求；
- 镇区A不能修改镇区B需求；
- 部门只能查看协调负责镇区，不得直接修改镇区需求；
- 两名团员并发认领，只允许一名成功；
- 平台往届不能成为正式主责；
- 普通管理员不能转交负责人；
- 超级管理员可按高风险流程转交；
- 团长不能因团长角色自动获得管理员审核；
- 团长久未更新提醒满足7天限频；
- 部长不能因 `MINISTER` 自动获得管理员审核、需求负责人转交或在任团员专属能力；
- 非 `MEMBER_CURRENT` 的部长不能仅凭 `MINISTER` 认领或协同需求；
- `MINISTER + MEMBER_CURRENT` 可通过多角色合并获得在任团员能力；
- 团长与部长的全团概览、全团共享行程、月度台账和久未更新提醒能力均有效；
- 部长久未更新提醒满足7天限频；
- 合并来源记录不能重复形成正式发布需求。

## 27.3 企业

- 所有内部用户可看正式联系人完整电话；
- 镇区只能维护本镇企业联系人；
- 停用主要联系人前必须存在新主要联系人；
- 普通团员不能正式新增企业；
- 企业合并必须管理员及以上且走高风险流程。

## 27.4 人才

- 普通内部用户可看正式人才；
- 团员可提交人才但不能正式发起镇区对接；
- 部门不能正式发起人才对接；
- 镇区只能发起本镇人才对接；
- 同人才+镇区不能并行两个活动轮次；
- 人才原推荐人历史不可静默覆盖。

## 27.5 报销

- 普通管理员无报销管理授权时无法查看他人报销；
- 部长不能因 `MINISTER` 查看他人报销或获得 `reimbursement.manage`；
- 报销管理人员可以核对但不能因此获得其他管理员权限；
- 平台内往届无申请权限时仍能查看本人历史报销；
- 敏感附件访问产生审计；
- “已提交财务”不会变成“已付款”。

## 27.6 办事求助

- 平台往届不能新建求助；
- 未授权人员不能查看他人求助；
- 部长不能因 `MINISTER` 查看他人求助；
- 被转交单位工作人员可以认领；
- 并发认领只产生一个主办人；
- 管理员可以重新分派。

## 27.7 AI

- 管理员不能读取他人完整荷宝对话；
- 超级管理员也不能读取他人完整荷宝对话；
- 部长不能读取他人完整荷宝对话；
- AI推荐名单仅规则指定主体可见；
- 模型输出不能绕过业务权限泄露联系方式。

## 27.8 系统

- 管理员不能查看完整审计；
- 管理员不能执行数据恢复；
- 非超级管理员不能进行需求负责人转交；
- 普通组织任职或职位名称不能自动产生管理员、团长、部长或报销管理权限；
- 部长角色撤销或到期后，团队协调能力立即失效；
- 部长不能查看完整审计、执行备份恢复或转交需求负责人。

# 28. Codex 开发红线

Codex在实现任何模块时必须遵守：

1. 不得绕过 Permission Service；
2. 不得将权限只写在前端；
3. 不得因为拥有 `ADMIN` 就默认开放所有敏感数据；
4. 不得因为拥有 `SUPER_ADMIN` 就开放他人私人 AI 对话正文；
5. 不得以职位名称字符串推导管理员等高权限；
6. 不得把角色核心语义做成普通后台可随意编辑配置；
7. 不得让业务状态只在页面端判断；
8. 不得在列表返回全量数据后再前端过滤数据范围；
9. 不得物理删除历史权限审计；
10. 不得通过修改数据库直接跳过高风险业务流程；
11. 不得实现“管理员万能 true”；
12. 不得将报销管理角色视作默认独立身份，必须作为附加敏感权限；
13. 不得让人员离岗后旧数据范围继续有效；
14. 不得让AI结果突破权限边界；
15. 不得在测试失败时删除权限测试来通过CI。

# 30. 权限计算伪代码

```ts
async function authorize(input: AuthorizationInput) {
  const actor = await loadActor(input.actorId)

  requireActiveAccount(actor)
  requireValidSession(actor)

  const capabilities = await resolveCapabilities(actor)
  requireCapability(capabilities, input.action)

  const scope = await resolveCurrentDataScope(actor)
  requireResourceInScope(scope, input.resource)

  const relations = await loadBusinessRelations(actor, input.resource)
  requireRelationIfNeeded(input.action, relations)

  requireStateAllowsAction(input.resource, input.action)

  requireSensitiveGrantIfNeeded(actor, input.action)

  return ALLOW
}
```

所有高风险写操作随后再执行：

```text
reason
→ impact preview
→ confirm
→ transaction
→ outbox event
→ audit log
```
