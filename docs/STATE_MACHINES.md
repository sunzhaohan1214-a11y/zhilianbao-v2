# 1. 总原则

## 1.1 状态必须由服务端控制

任何状态变化必须通过业务 Service 的显式 transition 执行。

禁止：

```ts
await prisma.demand.update({
  data: { status: "COMPLETED" }
})
```

绕过业务规则。

统一模式：

```ts
await demandService.transition({
  demandId,
  action: "APPROVE_CLOSE",
  actorId,
  reason
})
```

Service 必须同时完成：

1. 权限判断；
2. 最新状态判断；
3. 必填字段判断；
4. 数据范围判断；
5. 数据库事务；
6. 状态历史；
7. Outbox 业务事件；
8. 消息 / 待办后续处理；
9. 审计。

## 1.2 所有状态变更保留历史

至少保存：

```text
业务ID
旧状态
新状态
动作
操作人
操作时间
操作原因
来源入口
request_id
必要的前后快照
```

不得只保存“当前 status”。

## 1.3 终态不是物理删除

智链宝正式数据原则：

> 不物理删除，通过停用、撤回、取消、已合并、被替代和版本记录保留历史。

## 1.4 标签不得伪装成状态

例如正式需求：

- 紧急；
- 久未更新；
- 跨批次；

均是标签 / 派生属性，不是主状态。

## 1.5 “状态纠正”不是普通流程

管理员因误操作或线下事实需要纠正正式数据时：

- 不新增随意可走的普通状态箭头；
- 走正式纠错 / 状态纠正流程；
- 必须填写原因；
- 保留纠正前后状态；
- 产生审计；
- 必要时通知相关责任人。

错误合并恢复属于更高风险操作，由超级管理员处理。

# 2. 账号状态机

## 2.1 主状态

技术枚举：

```text
PENDING_ENABLE     待启用
UNACTIVATED        未激活
NORMAL             正常
DISABLED           已停用
```

标准流程：

```text
待启用
  ↓ 启用（首次从未完成改密）
未激活
  ↓ 首次登录 + 强制改密 + 保密确认
正常
  ↓ 停用
已停用
```

恢复：

```text
已停用
  ↓ 恢复
待启用
  ↓ 再次启用
未激活 / 正常
```

规则：

- 从未完成首次改密：再次启用后进入“未激活”；
- 已完成过首次改密：再次启用后恢复“正常”。

## 2.2 独立强制改密标记

密码重置不改变账号主状态。

独立字段：

```text
force_password_change = true | false
```

重置后：

```text
正常
+
force_password_change=true
+
全部Session失效
```

再次登录后只能进入改密流程。

完成改密：

```text
force_password_change=false
```

才允许业务访问。

## 2.3 禁止状态

- 待启用：不能登录；
- 已停用：不能登录；
- 未激活：只能进入首次激活流程；
- 正常 + 强制改密：只能进入改密流程。

# 3. 需求线索状态机

需求线索和正式需求必须使用两套独立状态机。

“待关联企业”不是正式需求状态。

## 3.1 技术枚举

```text
PENDING_TOWNSHIP_VERIFY    待镇区核验
PENDING_ENTERPRISE_LINK    待关联企业
NEED_MORE_INFO             待补充
MERGED                     已合并
CLOSED                     已关闭
CONVERTED                  已转正式需求
```

## 3.2 主流程

企业已存在：

```text
待镇区核验
   ├─ 信息不足 → 待补充
   │              ↓ 补充完成
   │          待镇区核验
   │
   ├─ 与其他线索重复 → 已合并
   ├─ 无效 / 不继续 → 已关闭
   └─ 核验完成 → 已转正式需求
```

企业未入正式库：

```text
待关联企业
   ↓ 企业新增申请
等待企业建档
   ↓
企业建档成功
   ├─ 内容仍不完整 → 待镇区核验
   └─ 企业和需求内容已完整核验 → 已转正式需求
```

## 3.3 来源不可变

任何流转均不得覆盖：

- 原始来源；
- 原始文字；
- 原始附件；
- 来源人员；
- 来源渠道；
- 来源时间；
- 原始企业填报 / 走访信息。

转正式需求时：

> 创建正式需求并建立来源关系，不把线索“改造成”正式需求而丢失原来源。

## 3.4 合并

线索合并后：

```text
MERGED
```

- 保留原始记录；
- 只读；
- 指向主记录；
- 不物理删除。

## 3.5 关闭与恢复

线索关闭：

```text
CLOSED
```

保留原因和历史。

误关闭：

- 管理员可恢复到合理的前置业务状态；
- 必须保留恢复历史。

错误合并：

- 按正式数据合并恢复规则处理；
- 高风险；
- 超级管理员根据审计恢复。

# 4. 正式需求状态机

## 4.1 主状态

技术枚举：

```text
DRAFT               草稿
PENDING_REVIEW      待审核
RETURNED            退回修改
PENDING_CLAIM       待对接
IN_PROGRESS         对接中
PENDING_CLOSE_REVIEW 待办结审核
COMPLETED           已办结
CANCELED            已取消
MERGED              已合并
```

标准主流程：

```text
草稿
 ↓
待审核
 ↓ 审核通过
待对接
 ↓ 认领 / 往届协助路径确认
对接中
 ↓ 提交办结
待办结审核
 ↓ 审核通过
已办结
```

## 4.2 审核退回

```text
待审核
  ↓ 管理员退回
退回修改
  ↓ 负责镇区修改并重新提交
待审核
```

管理员在待审核阶段不得为了“省一次退回”直接修改企业、联系人、标题、企业原始需求文本等核心字段。

## 4.3 办结退回

```text
待办结审核
   ↓ 管理员核实后退回
对接中
```

必须填写退回原因。

## 4.4 取消

允许从：

```text
待审核
退回修改
待对接
对接中
待办结审核
```

进入：

```text
已取消
```

执行人：

- 负责镇区；
- 管理员。

要求：

- 取消前线下沟通；
- 填写原因；
- 通知主责及协同；
- 保留全部历史；
- 不计为办结。

企业公开填报企业本身不能在线取消正式需求。

## 4.5 合并

管理员确认重复正式需求时：

```text
非主记录
→ 已合并
```

已合并是只读终态：

- 跳转到主记录；
- 保留原业务编号；
- 保留来源；
- 保留附件；
- 保留历史；
- 不计为正式新增发布需求的重复成果。

合并前必须预览关联影响。

错误合并恢复：

> 仅超级管理员根据完整审计执行。

## 4.6 待对接 → 对接中：在任认领

第一位合法的当前活动批次在任团员认领：

```text
PENDING_CLAIM
→ IN_PROGRESS
```

同一需求只能一名正式主责。

数据库必须防止并发双主责。

AI推荐与否不影响在任团员的合法主动认领资格。

## 4.7 待对接 → 对接中：往届协助

仅在：

- 在任无合适匹配；或
- 完整认领周期结束仍无人认领；

才启用往届补充推荐。

管理员确认往届愿意协助并指定镇区经办后：

```text
PENDING_CLAIM
→ IN_PROGRESS
```

但此时：

```text
formal_owner = null / 无在任主责
process_responsible_unit = 负责镇区
township_handler = 指定镇区经办人
alumni_helper = 往届协助人
```

往届不得被写成正式主责。

## 4.8 暂停

**不存在“暂停”主状态。**

受阻仍保持：

```text
IN_PROGRESS
```

并通过进展真实记录：

- 当前问题；
- 下一步；
- 阻碍；
- 更新时间。

## 4.9 久未更新

`STALE` 不是主状态。

它是派生关注标签，只能存在于符合规则的：

```text
IN_PROGRESS
```

需求上。

团长或部长通过团队协调能力发出的提醒不会改变主状态；提醒审计保留实际角色身份。

## 4.10 正式发布后纠错

已发布正式需求发生正式纠错时：

- 不通过退回流程改写历史；
- 管理员线下核实；
- 输入纠错原因；
- 生成正式数据新版本；
- 保留旧版本；
- 通知相关责任人；
- 主状态原则上保持原业务状态，除非明确执行“状态纠正”。

# 5. 需求参与关系状态

主责、协同、往届协助不应只存在当前字段，应保存生效历史。

## 5.1 协同申请

建议技术状态：

```text
PENDING
ACCEPTED
REJECTED
WITHDRAWN
```

主责确认后：

```text
PENDING → ACCEPTED
```

## 5.2 协同参与关系

建议：

```text
ACTIVE
LEFT
REMOVED
```

主动退出：

```text
ACTIVE → LEFT
```

主责移除：

```text
ACTIVE → REMOVED
```

均要求：

- 原因；
- 生效时间；
- 不删除历史进展；
- 不删除历史贡献；
- 发送相关消息。

# 6. 需求成效跟踪状态机

成效跟踪独立于需求主状态。

需求已经：

```text
COMPLETED
```

才进入成效跟踪判定。

## 6.1 跟踪主状态

```text
NOT_TRACKED    不跟踪
PENDING        待跟踪
IN_PROGRESS    跟踪中
ENDED          已结束
```

办结审核通过时管理员决定：

```text
不跟踪
```

或：

```text
待跟踪
+ 首次跟踪日期
```

到期并开始实际跟踪：

```text
待跟踪 → 跟踪中
```

每轮可：

```text
跟踪中
  ├─ 设置下次日期 → 继续跟踪中
  └─ 结束 → 已结束
```

## 6.2 每轮成效记录审核

产品规则要求：

> 镇区填报，管理员审核通过后才进入正式统计。

因此每一条成效跟踪记录建议使用独立审核状态：

```text
DRAFT
PENDING_REVIEW
RETURNED
APPROVED
```

这属于技术规格化状态，不改变需求本身 `COMPLETED` 主状态。

只有：

```text
APPROVED
```

进入正式统计。

# 7. 企业新增 / 纠错申请状态机

新增申请和纠错申请使用同一审批骨架：

```text
待审核
  ├─ 通过
  ├─ 退回修改
  └─ 已关闭
```

技术枚举：

```text
PENDING_REVIEW
APPROVED
RETURNED
CLOSED
```

退回：

```text
PENDING_REVIEW → RETURNED
```

修改后：

```text
RETURNED → PENDING_REVIEW
```

通过：

```text
PENDING_REVIEW → APPROVED
```

关闭：

```text
PENDING_REVIEW / RETURNED → CLOSED
```

管理员自身直接正式维护时，可以不创建普通审批流程，但仍必须生成正式版本和审计。

# 8. 正式企业状态机

正式企业只使用：

```text
NORMAL      正常
DISABLED    已停用
```

管理员：

```text
正常 → 已停用
```

需填写原因。

可恢复：

```text
已停用 → 正常
```

## 8.1 停用影响

已停用企业：

- 默认从普通列表隐藏；
- 默认从地图隐藏；
- 不允许新建正式需求。

但：

- 历史需求保留；
- 历史走访保留；
- 联系人保留；
- 成效保留；
- 已发布在办需求不自动取消。

在办需求由镇区 / 管理员按实际情况继续或取消。

## 8.2 企业合并

企业合并不是 `DISABLED`。

被合并企业进入独立只读合并状态 / 标记：

```text
MERGED
```

并指向主企业。

不物理删除。

错误合并恢复仅超级管理员。

---

# 9. 企业联系人状态

建议：

```text
ACTIVE
INACTIVE
```

禁止物理删除。

规则：

- 同企业同一时间只能一名有效主要联系人；
- 停用主要联系人前必须先指定新的主要联系人；
- 历史需求保存提交时联系人快照，不随当前联系人变化。

# 10. 人才新增 / 修改申请状态机

与企业申请相同：

```text
待审核
  ├─ 通过
  ├─ 退回修改
  └─ 已关闭
```

技术枚举：

```text
PENDING_REVIEW
APPROVED
RETURNED
CLOSED
```

团员、镇区、部门提交。

管理员：

- 审核；
- 通过；
- 退回；
- 关闭。

管理员自身直接正式新增 / 修改：

- 可直接生效；
- 仍保留版本和审计。

# 11. 正式人才状态

正式人才建议正式资源状态：

```text
ACTIVE
DISABLED
MERGED
```

其中：

- `ACTIVE`：正常可检索；
- `DISABLED`：管理员停用，不物理删除；
- `MERGED`：重复人才合并后的只读记录，跳转主记录。

合并恢复：

> 仅超级管理员按审计处理。

人才原推荐人形成正式数据后不可静默覆盖。

# 12. 人才—镇区对接轮次状态机

## 12.1 状态

产品业务状态：

```text
对接中
对接完成
已撤回
```

技术枚举：

```text
IN_PROGRESS
COMPLETED
WITHDRAWN
```

新建：

```text
NEW → IN_PROGRESS
```

完成：

```text
IN_PROGRESS → COMPLETED
```

撤回：

```text
IN_PROGRESS → WITHDRAWN
```

## 12.2 不允许重新打开

```text
COMPLETED
WITHDRAWN
```

都是该轮次终态。

后续出现新的合作事项：

> 新建一个新的对接轮次。

禁止：

```text
COMPLETED → IN_PROGRESS
WITHDRAWN → IN_PROGRESS
```

## 12.3 唯一活动轮次

同一：

```text
talent_id + township_id
```

同时最多一条：

```text
IN_PROGRESS
```

数据库必须通过约束 / 事务防止并发产生两个活动轮次。

## 12.4 误建软删除

只有管理员可软删除误建对接记录。

软删除：

- 不等同于镇区“撤回”；
- 记录仍保留审计；
- 统计中排除；
- 不物理删除。

# 13. 政策双状态模型

政策不是一个单一 status。

必须同时保存：

1. 发布状态；
2. 效力状态。

## 13.1 发布状态

```text
DRAFT       草稿
PUBLISHED   已发布
WITHDRAWN   已撤回
```

流程：

```text
草稿 → 已发布 → 已撤回
```

已撤回前端不作为正常政策展示，但历史和审计保留。

## 13.2 效力状态

```text
CURRENT     现行
REPLACED    已被替代
```

上传并发布新政策后，若管理员确认替代旧政策：

```text
新政策：CURRENT
旧政策：REPLACED
```

并保存双向关系。

## 13.3 禁止自动恢复

现行新政策被撤回：

```text
PUBLISHED/CURRENT
→ WITHDRAWN
```

系统**不得自动**执行：

```text
旧政策 REPLACED → CURRENT
```

管理员必须根据正式材料：

- 人工判断；
- 调整替代关系；
- 填写原因；
- 审计。

## 13.4 替代关系纠错

若替代关系本身设置错误：

管理员可以：

- 解除关系；
- 填写原因；
- 按事实把旧政策恢复 `CURRENT`；
- 保留全过程审计。

# 14. 来离宝状态模型

来离宝不需要人工审核状态。

主状态根据时间和取消标记计算。

建议技术派生状态：

```text
FUTURE       未来安排
IN_BAO       当前在宝
ENDED        已结束
CANCELED     已取消
```

判断：

```text
cancelled_at != null
→ CANCELED

当前时间 < 到宝时间
→ FUTURE

到宝时间 <= 当前时间 < 预计离宝时间
→ IN_BAO

当前时间 >= 预计离宝时间
→ ENDED
```

修改预计离宝时间后立即重新计算。

同一人员有效时间区间不得重叠。

取消：

- 必须原因；
- 保留记录；
- 不进入当前在宝；
- 不进入月度到宝统计。

# 15. 工作行程状态机

## 15.1 状态

产品状态：

```text
待进行
进行中
待补充结果
已完成
已取消
```

技术枚举：

```text
PLANNED
IN_PROGRESS
PENDING_RESULT
COMPLETED
CANCELED
```

流程：

```text
待进行 → 进行中 → 待补充结果 → 已完成
   └──────────────→ 已取消
进行中 ──────────→ 已取消
```

开始后参与人可以提前提交结果：

```text
进行中 → 已完成
```

不必强制先经过“待补充结果”的人工一步。

## 15.2 自动状态

最早节点时间前：

```text
PLANNED
```

到达最早节点时间：

```text
PLANNED → IN_PROGRESS
```

存在总体结束时间：

```text
结束时间到达
且无结果
→ PENDING_RESULT
```

未填写总体结束时间：

```text
行程日期结束
且无结果
→ PENDING_RESULT
```

## 15.3 结果提交

任一参与人提交有效总体结果：

```text
IN_PROGRESS / PENDING_RESULT
→ COMPLETED
```

同时：

- 所有参与人的该行程“待补充结果”待办关闭；
- 形成正式工作记录；
- 不需要管理员审核；
- 按关联企业生成走访记录。

## 15.4 取消

创建人 / 管理员按规则取消：

```text
PLANNED / IN_PROGRESS
→ CANCELED
```

取消：

- 通知参与人；
- 首页隐藏；
- 历史和审计保留。

最后一名参与人不能通过“退出参与”让行程无人负责，应由创建人或管理员正式取消。

# 16. 企业走访记录

企业走访不是审批流程。

生成规则：

```text
行程完成
↓
每个关联企业节点
↓
生成一条走访主记录
```

唯一性：

```text
trip_id + enterprise_id
```

只能生成一条走访主记录。

行程后续修改不得再次重复生成。

参与人可追加补充，不覆盖他人补充历史。

走访可生成一条或多条不同需求线索。

# 17. 报销状态机

## 17.1 主状态

产品状态：

```text
草稿
待线上核对
退回修改
已核对（待交纸质材料）
已收材料
已提交财务
```

技术枚举：

```text
DRAFT
PENDING_ONLINE_REVIEW
RETURNED
VERIFIED_WAITING_PAPER
PAPER_RECEIVED
SUBMITTED_TO_FINANCE
```

主流程：

```text
草稿
 ↓ 申请人提交
待线上核对
 ├─ 退回 → 退回修改
 │           ↓ 修改后重新提交
 │       待线上核对
 │
 └─ 核对通过
      ↓
已核对（待交纸质材料）
      ↓ 确认收到
已收材料
      ↓ 交财务
已提交财务
```

## 17.2 核对前撤回

报销管理人员核对前：

```text
待线上核对
 ↓ 申请人撤回
草稿
```

历史提交版本保留。

## 17.3 待交纸质材料退回线上修改

如发现线上内容错误：

```text
已核对（待交纸质材料）
→ 退回修改
```

修改后：

```text
退回修改 → 待线上核对
```

重新核对。

## 17.4 已收材料发现不完整

允许：

```text
已收材料
→ 已核对（待交纸质材料）
```

用于重新等待补齐纸质材料。

必须原因和历史。

## 17.5 状态纠正

报销管理人员发生误操作时允许正式状态纠正。

要求：

- 原因必填；
- 纠正前状态；
- 纠正后状态；
- 操作人；
- 时间；
- 审计。

特别是：

> “已提交财务”状态纠正只修正系统记账，不得被描述为改变线下财务事实。

## 17.6 最终状态语义

```text
SUBMITTED_TO_FINANCE
```

只表示：

> 报销管理人员已将纸质材料交给财务。

不表示：

- 财务审核通过；
- 已付款；
- 财务审批完成。

V2第一阶段不增加“已付款”状态。

# 18. 办事求助状态机

## 18.1 主状态

```text
待受理
处理中
已办结
已撤回
```

技术枚举：

```text
PENDING
IN_PROGRESS
COMPLETED
WITHDRAWN
```

主流程：

```text
待受理
  ↓ 接手 / 指定处理人
处理中
  ↓ 主办人填写结果
已办结
```

撤回：

```text
待受理
  ↓ 提交人撤回
已撤回
```

重新打开：

```text
已办结
  ↓ 提交人填写重新打开原因
处理中
```

## 18.2 唯一主办人

被转交单位全体在岗人员可看到待办。

第一位合法点击“接手”的人员成为：

> 唯一当前主办人。

服务端必须处理并发。

## 18.3 重新分派

管理员可以在处理中因：

- 主办人离岗；
- 无法处理；
- 业务需要；

重新分派。

这属于办事求助自身的负责人管理。

**不属于需求负责人转交**，不要求超级管理员。

## 18.4 超期

预计完成日期不是主状态。

超期为派生标签：

```text
OVERDUE = IN_PROGRESS
          && now > expected_complete_at
```

超期进入管理员待办，但不新增“已逾期”主状态。

# 19. 公告状态机

## 19.1 发布状态

```text
草稿
已发布
已撤回
```

技术枚举：

```text
DRAFT
PUBLISHED
WITHDRAWN
```

流程：

```text
草稿 → 已发布 → 已撤回
```

撤回后：

- 前端正常入口隐藏；
- 历史审计保留。

## 19.2 内容版本

已发布公告：

- 标题修改；
- 正文修改；
- 附件修改；

均：

> 创建新的内容版本，不静默覆盖。

若公告“需确认”：

> 内容新版本发布后，旧确认失效，目标用户重新确认。

## 19.3 置顶和范围不是正文版本

仅：

- 调整置顶；
- 调整目标范围；

不生成正文新版本。

但必须：

- 保留操作历史；
- 更新访问权限；
- 按规则生成消息。

# 20. 公告确认状态

对每个“公告版本 + 用户”独立保存：

```text
UNREAD
READ
CONFIRMED
```

普通公告：

```text
UNREAD → READ
```

需确认公告：

```text
UNREAD → READ → CONFIRMED
```

实质内容生成新版本后：

> 为新版本重新创建用户确认关系。

不得覆盖旧版本历史确认。

---

# 21. 消息状态

消息只需要个人阅读状态：

```text
UNREAD
READ
```

业务被取消 / 合并 / 撤回不删除历史消息。

用户点击旧消息时：

- 如果业务已取消：明确展示已取消；
- 已合并：跳转主记录并说明；
- 已撤回：明确说明；
- 无权限：显示无权状态；
- 不出现空白页。

---

# 22. 待办状态

建议技术状态：

```text
OPEN
COMPLETED
CLOSED_INVALID
```

- `OPEN`：当前用户现在能执行；
- `COMPLETED`：用户执行对应动作完成；
- `CLOSED_INVALID`：由于业务状态、权限或负责人变化自动失效。

同一：

```text
business_type
+ business_id
+ todo_type
+ assignee
```

原则上只保留一条有效 `OPEN` 待办。

待办关闭不得删除历史。

---

# 23. 企业 / 人才正式数据合并通用状态

正式重复实体：

```text
ACTIVE
→ MERGED
```

合并后：

- 被合并记录只读；
- 保留编号；
- 保留来源；
- 保留历史；
- 自动跳转主记录。

合并前：

- 预览所有关键关联；
- 明确主记录；
- 管理员确认。

错误合并恢复：

> 仅超级管理员。

恢复不得通过简单把 `MERGED=false` 实现，必须按原关联映射进行受控恢复。

# 24. 状态与“停用 / 撤回 / 取消 / 合并”的区别

Codex不得混用。

| 概念 | 用途 |
|---|---|
| 停用 | 正式资源当前不再正常使用，如企业、人才、账号 |
| 撤回 | 已主动退出某个流程或发布，如公告、人才对接、求助提交前 |
| 取消 | 已存在业务事项不再继续，如正式需求、行程 |
| 合并 | 重复正式记录保留为只读来源并指向主记录 |
| 退回修改 | 不是终止，修改后可重新提交 |
| 已关闭 | 线索 / 申请类流程不再继续，但保留记录 |
| 已办结 / 已完成 | 业务正常完成终态 |

# 26. 事务规则

一次业务 transition 中，下列内容必须保证一致性：

```text
主记录状态
+ 参与关系
+ 状态历史
+ 必要快照
+ Outbox Event
```

例如认领：

```text
需求 PENDING_CLAIM → IN_PROGRESS
+ 新增主责关系
+ 关闭认领到期相关状态
+ 状态历史
+ outbox: DEMAND_CLAIMED
```

必须同一事务提交。

不能出现：

> 需求已显示“对接中”，但主责为空。

# 27. 状态机并发保护

必须测试并保护：

### 需求认领

两人同时：

```text
PENDING_CLAIM → IN_PROGRESS
```

只一人成功。

### 办事求助接手

多人同时接手：

> 只有一名唯一主办人。

### 人才对接

同一人才 + 同一镇区同时创建：

> 只允许一条 `IN_PROGRESS`。

### 主要企业联系人

并发修改：

> 同企业只能一个有效主要联系人。

### 报销

管理员核对和申请人撤回同时发生：

> 只能有一个合法 transition 成功，不产生互相矛盾状态。

# 28. 统计不得自己发明状态

统计只使用本文件定义的正式状态与时间。

例如需求月末存量只统计互斥主状态：

```text
PENDING_REVIEW
RETURNED
PENDING_CLAIM
IN_PROGRESS
PENDING_CLOSE_REVIEW
```

“久未更新”是 `IN_PROGRESS` 子集，不能再加到存量总和中。

已办结量以：

> 管理员办结审核通过时间

为统计时间。

人才“月末对接中”：

> 只统计 `TalentTownshipRound.IN_PROGRESS`。

成效：

> 只统计审核通过的成效记录。

# 29. 状态枚举禁止后台随意配置

以下属于产品版本规则：

- 正式需求主状态；
- 需求核心流转；
- 报销主状态；
- 办事求助主流程；
- 企业 / 人才正式状态语义；
- 政策发布与效力状态；
- 人才对接终态语义。

后台不能提供：

> “新增一个需求状态”

> “把已提交财务改名成已付款”

> “允许往届直接成为正式主责”

这种自由配置。

如需改变：

```text
PRD新版本
↓
STATE_MACHINES新版本
↓
数据库Migration
↓
代码
↓
测试
↓
正式应用版本
```

# 30. Codex 状态机红线

1. 不得直接赋值正式业务状态；
2. 不得把标签当主状态；
3. 不得新增PRD未批准的“暂停”等状态；
4. 不得物理删除终态历史；
5. 不得让 AI 改状态；
6. 不得让定时任务自动办结需求、人才对接或求助；
7. 不得自动把被替代旧政策恢复现行；
8. 不得允许已完成 / 已撤回的人才对接轮次重新打开；
9. 不得把“已提交财务”解释为已付款；
10. 不得让往届协助人写入正式主责字段；
11. 不得因企业停用自动取消已发布需求；
12. 不得因行程纠错静默覆盖已经形成的正式下游需求；
13. 不得通过前端状态判断替代服务端事务内判断；
14. 不得跳过状态历史和Outbox事件；
15. 不得通过自由后台配置改变核心状态机。
