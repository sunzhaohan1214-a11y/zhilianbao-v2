# 智链宝 V2.0 — MIGRATION_PLAN.md

> 版本：v1.0  
> 状态：开发基线  
> 范围：V1 → V2 全量业务数据与附件迁移。

## 1. 原则

1. V1 正式系统在 V2 开发期继续运行；
2. V2 LOCAL/TEST 绝不连接 V1 正式库做开发；
3. 迁移工具只读 V1，写 V2；
4. 每条迁移保存源系统、源表/类型、源ID；
5. 迁移幂等，可重复演练；
6. 无法映射数据进入异常清单，不静默丢弃；
7. 附件和结构化数据一起对账；
8. 正式切换前保留完整 V1 备份；
9. V1 下线后不向普通用户提供额外只读入口；
10. 迁移失败不得用“手工改生产库”绕过。

## 2. 环境

```text
V1 PROD          保持运行
V2 MIGRATION DB  全量迁移演练专用
V2 TEST          功能/UAT
V2 PROD          正式切换目标
```

迁移演练建议使用 V1 脱敏或受控只读快照。

## 3. 统一匹配/去重引擎

在线新增、Excel导入、V1迁移、正式合并必须共用同一套 EntityMatcher。

禁止四套不同去重规则。

### Person

优先：

```text
手机号完全一致
```

但以下进入人工异常：

- 缺手机号；
- 重复手机号；
- 格式错误；
- 一人多档；
- 同名异人；
- 旧数据明显复用号码。

不得仅凭姓名自动合并。

### Enterprise

优先：

```text
统一社会信用代码
```

无代码：

```text
标准化企业名称 + responsible_area
```

只作为候选，人工确认。

### Talent

候选：

```text
姓名
+ 单位
+ 专业方向
```

只提示重复，管理员确认合并。

### Policy

候选：

```text
标题
+ 发布部门
+ 日期
+ 主文件SHA256
```

不因标题相似自动合并。

## 4. LegacyMigrationMap

唯一键：

```text
source_system + source_entity + source_id
```

已存在映射：

> 重跑时更新/校验，不重复创建。

## 5. 人员和账号

V1账号：

- 按手机号匹配 Person；
- 不迁移旧密码；
- 符合开户条件者新密码重置为手机号后6位；
- 初始 `PENDING_ENABLE`；
- 批量启用后首次登录强制改密；
- 历史往届只建档，不默认开户；
- 通讯录先确认当前在岗再开户。

旧领导不得通过修改姓名/手机号变成新领导。

## 6. 组织

迁移：

- 镇区/园区组织；
- 部门；
- 派出单位；
- 挂职单位；
- 当前人员任职。

V2新增：

```text
AdministrativeArea
OrganizationAreaMapping
DepartmentTownshipRelation
```

V1 无法提供完整历史时：

> 当前有效关系迁移为当前基线；可识别的历史关系保留。

不得伪造未知历史。

## 7. 企业

迁移：

- 主档；
- 地址；
- 信用代码；
- 法人；
- 简介；
- 主营产品；
- 标签；
- 联系人；
- 当前区域归属。

联系人：

- 不物理删除；
- 若 V1 无主要联系人标志，可按已知数据人工确认；
- 不自动猜主联系人。

坐标：

- 有可靠坐标则迁移；
- 无坐标进入地图待完善；
- 不通过坐标反推区域。

## 8. 需求

V1状态：

```text
待对接 → PENDING_CLAIM
已对接 → IN_PROGRESS
已解决 → COMPLETED + legacy_migrated
```

历史已解决：

- 不重新审核；
- 不强制补成效。

V1类型：

```text
技术需求 → TECHNICAL
人才合作 → TALENT
落地需求 → PROJECT
为空/无法识别 → OTHER
```

必须保留：

- 原V1 ID；
- 原标题；
- 原描述；
- 原企业；
- 原联系人；
- 历史负责人；
- 进展；
- 附件；
- 来源标志。

若历史数据没有完整状态时间线：

> 迁移当前状态并保存 V1 原始快照，不伪造每一步时间。

## 9. 来离宝

旧记录作为历史保留。

**不用于新版“当前在宝”实时统计。**

正式切换后：

> 当前在宝人员重新填报新版记录。

避免旧预计时间错误导致首页人数失真。

## 10. 行程 / 走访

若 V1数据结构无法稳定映射到新版多节点 Trip：

- 保留为历史工作记录；
- 有明确企业关系时可建立历史 Visit；
- 不强行生成虚假的多节点行程。

迁移后新业务按 V2 Trip 结构运行。

## 11. 人才

迁移：

- 人才正式信息；
- 原材料；
- 可识别推荐人；
- 历史对接记录。

禁止从简历自动抽取人才本人电话形成结构化字段。

推荐人无法确定：

> 异常清单人工指定内部推荐责任人。

## 12. 政策

迁移：

- 政策主文件；
- 补充文件；
- 标题/部门/日期；
- 当前可识别状态。

V1若没有可靠“替代关系”：

> 不自动猜关系。

## 13. 报销

V1：

```text
审核中 → PENDING_ONLINE_REVIEW
已退回 → RETURNED
已通过 → LEGACY_VERIFIED_TERMINAL
```

`LEGACY_VERIFIED_TERMINAL` 作为迁移兼容历史状态/标识处理：

> 不进入新纸质材料流转。

不得把旧“已通过”自动变成“已提交财务”。

旧票据全部迁移并校验。

## 14. 办事求助

迁移：

- 提交人；
- 类别；
- 说明；
- 当前/历史处理人；
- 结果；
- 附件。

旧类别无法映射：

```text
OTHER
+ 保留原类别快照
```

## 15. 公告

迁移历史公告时：

- 保留正文和附件；
- 如V1没有可靠“确认记录”，不得伪造已确认；
- 可标记 `legacy_migrated`。

## 16. 附件

迁移范围至少：

- 需求；
- 团员照片；
- 企业；
- 人才简历/材料；
- 政策；
- 报销票据；
- 求助；
- 公告。

每个文件：

```text
源文件存在?
→ copy
→ SHA256
→ size
→ target COS
→ re-read metadata
→ AttachmentLink
```

异常：

```text
MISSING
CORRUPTED
COPY_FAILED
HASH_MISMATCH
```

进入报告。

## 17. 迁移批次

```text
MigrationBatch
```

保存：

- 开始/结束；
- V1快照时间；
- 代码版本；
- 映射版本；
- 操作人；
- 各表结果；
- 附件结果；
- 最终签字。

## 18. 演练顺序

### 演练1：20–30条脱敏样本

验证：

- 字段；
- 关系；
- 权限；
- 附件；
- 状态。

### 演练2：一次完整全量迁移

输出差异。

修复后可再重复全量，直到关键数量可对平。

## 19. 对账报告

每模块至少：

```text
源记录数
成功数
失败数
跳过数
合并数
待人工确认数
附件总数
附件成功数
附件异常数
```

同时抽样验证：

- 需求→企业；
- 需求→联系人；
- 人员→账号；
- 人员→任职；
- 团员→批次；
- 报销→票据；
- 政策→主文件。

## 20. 正式切换

```text
1. 宣布切换窗口
2. V1停止新增/修改
3. V1最终备份
4. V2 PROD发布前快照
5. 最终增量迁移
6. 附件校验
7. 数量对账
8. 人工异常处理
9. 关键UAT/Smoke
10. 放行V2
11. 下线V1
```

## 21. 中止条件

出现任一项：

- 核心表数量无法对平；
- 账号匹配明显错误；
- 关键附件大面积缺失；
- 权限隔离失败；
- 核心需求闭环不可用；
- 报销数据可见性错误；
- Migration不可重复执行。

则：

> 不开放 V2。

切换窗口内：

- 恢复 V1 写入；或
- 回到切换前快照后重新迁移。

## 22. 切换后的回退

代码问题：

> 回滚代码，不恢复数据库。

如果正式数据迁移本身错误且必须重来：

> 进入维护模式，基于切换前快照和已批准Runbook执行恢复/重新迁移。

不得临时手改大量生产记录。

## 23. 迁移红线

1. 不迁移V1密码；
2. 不默认给历史往届开户；
3. 不因同名自动合并人员；
4. 不因企业名称相似自动合并；
5. 不丢原V1 ID；
6. 不静默丢无法映射字段；
7. 不用坐标改企业区域；
8. 不将旧已通过报销解释为已付款/已提交财务；
9. 不用旧来离宝算新版当前在宝；
10. 不在V1正式库执行清理/修改迁移脚本。
