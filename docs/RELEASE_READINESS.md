# Release Readiness

M3-008 separates code completion, configuration presence and real production verification. The canonical machine-readable evidence is generated by `npm run release:check -- --mode=<ci|prod>` into `artifacts/release-readiness.json` and `.md`.

## Status vocabulary

- `PASS`: evidence exists and the check passed.
- `FAIL`: a reachable check failed; production mode exits non-zero.
- `BLOCKED_BY_EXTERNAL_ENV`: cloud/account/runtime evidence is unavailable.
- `BLOCKED_BY_SOURCE_DATA`: required V1 source snapshot or reconciliation evidence is unavailable.
- `BLOCKED_BY_UAT`: formal business sign-off is absent.
- `NOT_APPLICABLE`: explicitly reviewed and not applicable.

No blocked state may be translated into PASS. `RELEASE_READY=YES` requires production mode and every production-required gate to be PASS or explicitly NOT_APPLICABLE. Local/CI mode proves that gate code is reachable but always emits `RELEASE_READY=NO`.

## Candidate and immutable evidence binding

`APP_VERSION` must be the exact 40-hex candidate commit. `GITHUB_CANDIDATE_RUN_ID` identifies the immutable Actions run; the gate fetches it and requires the run `head_sha` plus all seven named jobs to match and succeed.

External evidence variables contain a JSON pointer rather than a self-reported result or boolean: `FILE_SCANNER_EVIDENCE_JSON`, `CLOUD_BACKUP_EVIDENCE_JSON`, `MAINTENANCE_EVIDENCE_JSON`, `RESTORE_DRILL_EVIDENCE_JSON`, `V1_REHEARSAL_EVIDENCE_JSON`, `UAT_EVIDENCE_JSON`, and `PROD_PREFLIGHT_EVIDENCE_JSON`. A local pointer contains an immutable digest and a readable evidence file path:

```json
{
  "reference": "urn:sha256:<64-hex-content-digest>",
  "sourcePath": "<path-to-evidence-json>"
}
```

An HTTPS reference may be used without `sourcePath` only when the URL contains a `sha256=<64-hex-content-digest>` query parameter. The readiness gate reads the referenced bytes, limits evidence to 1 MiB, recomputes SHA-256, and rejects missing sources or digest mismatches before parsing the evidence document. The referenced document must contain:

```json
{
  "category": "<scanner|backup|maintenance|restore|migration|uat|preflight|ai>",
  "candidateSha": "<40-hex-candidate-commit>",
  "environment": "<TEST|PROD>",
  "status": "PASS",
  "verifiedAt": "<ISO-8601 timestamp>",
  "details": {}
}
```

Each variable is bound to one category and environment; category or environment substitution fails closed. Scanner details must prove ClamAV health, clean acceptance and EICAR rejection. Backup details must prove a PROD source, the approved CynosDB region/cluster, provider health, a successful backup and a real snapshot time no older than 24 hours. Maintenance must prove provider health plus enter/exit checks. Restore must identify the exact TEST source backup and cluster, the TEST target cluster, validation, RTO/RPO and completed cleanup. UAT must prove zero P0/P1 issues plus business and operations sign-off. Production preflight must prove checks, rollback readiness and an approved change window. Missing category fields fail closed. Legacy naked booleans and inline self-reported PASS objects are ignored.

Migration evidence has an additional fail-closed FULL contract. Its `snapshotManifest` must be an immutable evidence pointer to the real `snapshot.json`; the gate reads, hashes and parses that file itself, requires its own `snapshotKind=FULL`, and binds its `snapshotId`, digest, and every file count/SHA-256 to the outer evidence. It also requires `FULL_REHEARSAL/COMPLETED` and one row for every current V1 contract entity file plus `attachments/manifest.ndjson`. The attachment inventory must bind to that exact manifest row and prove every source attachment was copied and re-read with matching hash, with zero issues. Evidence must identify distinct dry-run, apply batch/run and rerun batch/run executions, the dedicated target migration database, and zero unresolved BLOCKER or REVIEW issues. It must include exactly one row for every migration module and `ATTACHMENT`; each row must satisfy both source and attachment reconciliation equations, with zero failed, review or attachment-issue counts. All dry-run/apply/rerun/reconciliation booleans must still be true. A real SAMPLE manifest relabelled FULL in outer evidence, omitted files/modules, duplicate identities, mismatched digests/counts, or arithmetically invalid rows fail with `MIGRATION_EVIDENCE_INCOMPLETE`.

## Approved CynosDB identity

Real CynosDB operations require deployment-injected approved identity values: `CYNOSDB_APPROVED_ENVIRONMENT`, `CYNOSDB_APPROVED_CLUSTER_ID`, `CYNOSDB_APPROVED_REGION`, `CYNOSDB_APPROVED_VPC_ID`, and `CYNOSDB_APPROVED_SUBNET_ID`. They must match the requested configuration and the identity returned by Tencent Cloud. `APP_ENV` is not accepted as cloud-resource identity by itself. Restore drills additionally require the approved environment to be `TEST`; production backup readiness requires evidence for the approved `PROD` cluster. Keep real IDs in Secret/deployment configuration, not Git.

## Current M3-008 truth

Code automation covers security headers, dependency/secret/dangerous-code scans, real ClamAV CI integration, fixed-scale MySQL performance, Chromium/Firefox/WebKit compatibility, weak-network behavior, AI contract evaluation, CynosDB backup integration, guarded restore-to-new-cluster tooling, and read-only consistency audit.

The following remain external and therefore keep `RELEASE_READY=NO`: exact-candidate review/CI, UAT sign-off, a real V1 FULL rehearsal satisfying the expanded manifest/attachment/run/reconciliation contract, production scanner configuration, real production backup evidence, real restore drill and cleanup evidence, production maintenance integration, and production cutover preflight. This draft does not claim that any of those external gates has completed.

## Operator commands

```bash
npm run release:check -- --mode=ci
APP_ENV=prod APP_VERSION=<40-hex-commit> GITHUB_CANDIDATE_RUN_ID=<run-id> npm run release:check -- --mode=prod
```

The production command is a gate, not a deployment command. It creates no cloud resources and changes no data.
